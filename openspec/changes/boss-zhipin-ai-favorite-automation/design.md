## Context

当前扩展已具备 Vue 3 + Element Plus 的基础壳层和 Chrome MCP 集成能力，但业务流程仍停留在手动读取/写入演示阶段，无法支撑“BOSS 直聘候选人自动评估收藏”的实际作业。新需求同时覆盖 UI 信息架构调整、配置管理、页面自动化编排与外部大模型服务调用，属于跨模块改造。

关键约束如下：
- 页面 I/O 仍需通过 `chromeMcpService` 统一入口，UI/composable 不得直接访问 `chrome.*`。
- 配置必须持久化在 `localStorage`，且分为基础设置与高级设置。
- 目标站点默认为 `www.zhipin.com`，但允许用户修改。
- 自动化操作需在每个候选人处理后随机等待 1-5 秒，降低高频点击风险。
- 当前迭代不处理候选人筛选条件构建，仅处理“已在候选列表页面”后的自动化流程。

## Goals / Non-Goals

**Goals:**
- 在主界面提供以 prompt 为中心的执行入口，并增加设置入口。
- 提供设置面板，支持基础（域名等）与高级（API Key 等）配置并落盘。
- 在可用站点中执行候选人流程：读取列表 → 进入详情 → 提取简历 → 调用 LLM → 决策收藏。
- 为自动化流程提供可观测状态与错误反馈。
- 引入随机等待策略，控制操作节奏。

**Non-Goals:**
- 不实现候选人筛选条件自动配置。
- 不实现多站点复杂策略编排（仅提供单域名或用户输入域名匹配）。
- 不实现完整反爬对抗系统（仅实现基础随机等待）。
- 不约束具体大模型厂商，仅定义通用 API 配置与调用接口。

## Decisions

1. 设置模型与存储层拆分
- 决策：新增 settings service（如 `src/services/settingsService.ts`）封装 `localStorage` 的读取、校验、默认值合并与写入。
- 原因：避免 UI 组件中直接散落存储键名与序列化细节，便于后续迁移到 `chrome.storage`。
- 备选：直接在组件中读写 `localStorage`。放弃原因：耦合高、难测试、难扩展。

2. 主界面信息架构重构
- 决策：在 popup 顶部右侧提供设置按钮，通过抽屉或对话框承载“基础/高级设置”；主内容区保留 prompt 输入、执行按钮与状态展示。
- 原因：满足用户将核心行为聚焦在 prompt 驱动执行，同时保留配置入口。
- 备选：独立设置页面。放弃原因：切换成本高，且当前需求强调在主页面右上角入口。

3. 自动化编排层引入
- 决策：在 composable（或新增 orchestrator service）中实现顺序编排：
  1) 校验站点与配置；
  2) 读取候选人列表；
  3) 遍历候选人执行详情读取 + LLM 评估 + 收藏动作；
  4) 记录结果并随机等待。
- 原因：保持 `chromeMcpService` 聚焦单步页面 I/O，编排逻辑放在上层，职责清晰。
- 备选：在 `chromeMcpService` 内部实现全流程。放弃原因：服务职责过重，不利于复用与测试。

4. LLM 调用适配层
- 决策：新增 `llmService` 抽象（输入：prompt + 简历文本 + 候选人上下文；输出：是否收藏、理由）。
- 原因：将第三方 API 协议与 UI 业务逻辑隔离，便于未来更换模型提供商。
- 备选：在 UI/composable 直接 `fetch`。放弃原因：难以统一错误处理与重试策略。

5. 随机等待策略
- 决策：每个候选人处理结束后插入随机延时 $t \in [1,5]$ 秒。
- 原因：降低固定频率行为特征。
- 备选：固定 2 秒。放弃原因：模式过于稳定，风险更高。

## Risks / Trade-offs

- [风险] 页面 DOM 结构与选择器不稳定导致读取/点击失败 → [缓解] 将页面元素定位配置化，并提供失败重试与跳过策略。
- [风险] LLM 响应延迟导致流程耗时较长 → [缓解] 增加单候选人超时控制与可中断机制。
- [风险] `localStorage` 中存储 API Key 存在安全性不足 → [缓解] 明确提示风险并保留后续迁移 `chrome.storage` + 加密方案。
- [风险] 误收藏带来业务噪声 → [缓解] 记录判定理由，支持后续回溯与阈值调优。
- [权衡] 先做单流程串行而非并行 → [收益] 降低复杂度与风险；[代价] 总处理时长更长。
