## Context

自由指令模式已上线，但有两个可用性缺口：新用户不知道能力边界，满意的结果无法保存复用。这两个功能都纯扩展侧，不碰 BFF 与 agent-kit。

## Goals / Non-Goals

**Goals**
- 让用户一眼知道自己能下什么指令、指令能触发什么操作。
- 工具失败时给用户可读的反馈而非错误码。
- 用户能把满意会话存为技能，后续一键预填复用。

**Non-Goals**
- 不做技能的自动执行 -- 避免在错误页面上跑出非预期动作。
- 不做技能分享或导入导出。
- 不做技能的参数化（不支持占位符替换）。
- 不优化 context 裁剪策略 -- 那是另一个大工程。

## Decisions

### D1：工具说明硬编码在扩展侧，不从 BFF 拉取

9 个工具的名称与描述在 BFF 的 `browser-tools.ts` 里已有，但让扩展运行时拉取会增加一个异步依赖与失败路径。工具集变动频率极低，直接在扩展侧 `toolsCatalog.ts` 硬编码一份中文说明即可。两边不同步的风险用注释标注。

### D2：首次引导用 storage 标记，不用时间戳

用 `chrome.storage.local` 存一个 `boos.onboarding.toolsHelpSeen` 布尔值。首次打开 sidepanel 时检查，未看过就自动弹出说明面板。用户关闭后标记为已看。简单可靠，不依赖时间戳推断。

### D3：错误文本映射放在 controller，不在 toolExecutor

`toolExecutor` 的职责是执行与结构化失败，不该关心 UI 文案。映射逻辑放在 `useFreeFormController` 里：拿到 `ToolFailure` 后转成人话存进 `ConversationTurn`。这样测试时 executor 的行为不变，文案调整也不碰执行逻辑。

### D4：技能只存首条指令 + 轮次摘要，不存完整工具调用记录

完整轮次（含每步的工具输入输出）体积大且大部分是过程噪音。技能的核心是「用户想做什么」与「结果是什么」，所以只存：
- 名称（默认首条指令摘要）
- 首条用户指令（一键应用时预填）
- agent 的最终回复（让用户记得这个技能干了什么）
- 创建时间

这样一条技能很小，列表加载快，也不会撑爆 storage。

### D5：一键应用 = 新会话 + 预填指令，不自动执行

点击应用后：开新会话、把技能的首条指令填进输入框、聚焦输入框。用户看到后可以改、可以执行。不自动执行的原因：技能可能在特定页面才有意义，自动执行到错误页面会产生非预期动作（尤其是写操作）。

### D6：技能管理与设置分开，作为独立面板

技能是高频查看的功能（比设置频繁），放在设置抽屉里会多一步操作。做成独立面板，从 sidepanel 头部入口进入。技能列表用卡片式展示，每张卡片有名称、摘要、应用与删除按钮。

## Risks / Trade-offs

- **工具说明与 BFF 不同步** -> 两边都有注释提醒同步。工具集变动频率极低，风险可接受。
- **技能只存摘要不够详细** -> 这是刻意的。用户要的是「收藏好用的指令 + 一键再跑」，不是完整的会话回放。需要完整回放时可以去看会话列表。
- **一键应用不自动执行** -> 多一步点击。但避免了在错误页面自动操作的风险，这个代价值得。
- **storage 配额** -> 技能上限 50 条，每条很小（名称 + 一条指令 + 一句摘要），不会触及配额。

## Migration Plan

纯新增功能，无迁移。技能与首次引导标记都是新增的 storage key，不影响既有数据。
