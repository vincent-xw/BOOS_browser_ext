## Context

当前仓库尚未具备浏览器插件工程结构，也没有前端界面、插件入口或页面操作抽象层。本次变更的目标不是实现完整业务，而是先建立一个可持续演进的浏览器插件基础架构，使后续 capability 可以在稳定的 UI 容器、消息边界与页面操作接口之上逐步实现。

该项目要求界面技术栈使用 Vue 3 与 Element Plus，并且需要提供一个简单界面来触发页面读取与页面写入操作。由于后续功能细节尚未确定，本次设计需要尽量降低未来扩展 Popup、独立页、Side Panel、更多页面动作或更复杂状态管理时的重构成本。

## Goals / Non-Goals

**Goals:**
- 建立适用于浏览器插件的前端工程骨架，并支持至少一个可运行的交互入口。
- 采用 Vue 3 + Element Plus 构建一个简单但可扩展的插件界面。
- 将页面读写能力收敛到独立的 Chrome MCP 访问层，避免 UI 组件直接依赖底层调用细节。
- 定义读取页面、写入页面、错误反馈与忙碌状态的统一交互模型。
- 为后续扩展更多 capability 预留模块边界与目录约定。

**Non-Goals:**
- 不在本次变更中定义具体业务场景、复杂页面自动化流程或领域规则。
- 不要求一次性支持 Popup、Side Panel、Options、DevTools 等所有插件入口。
- 不实现复杂权限申请向导、账号体系、远程配置或云端同步能力。
- 不绑定某一种不可替换的 MCP 服务实现细节，保留后续适配空间。

## Decisions

### 1. 采用“插件壳 + 共享应用层 + MCP 适配层”的分层结构
- **Decision:** 将项目划分为插件入口层、共享 UI / 状态层、Chrome MCP 访问层三部分。
- **Rationale:** 这样可以避免 Vue 组件与浏览器插件环境或 MCP 调用细节强耦合，后续无论扩展更多 UI 入口还是替换页面操作实现，都只需要在边界层调整。
- **Alternatives considered:**
  - 直接在页面组件中调用 MCP：实现快，但后续难以测试和复用。
  - 先只做单文件原型：短期轻便，但会把“基础架构搭建”变成后续重构债务。

### 2. UI 入口采用“先提供一个简单主入口，结构上支持后续多入口扩展”
- **Decision:** 本次只要求落地一个简单可运行界面，但目录和共享层设计必须支持后续新增 Popup / Side Panel / Options 等入口。
- **Rationale:** 当前需求强调基础架构优先，过早铺开全部入口只会增加噪音；而只做一个完全不可扩展的入口又违背本次目标。
- **Alternatives considered:**
  - 一次性创建全部入口：更完整，但会引入不必要样板代码。
  - 仅做不可复用的单入口：初始最省事，但未来扩展成本高。

### 3. 前端栈固定为 Vue 3 + Element Plus，并优先选择对浏览器插件友好的构建方案
- **Decision:** UI 层统一使用 Vue 3 组合式 API 与 Element Plus 组件体系；构建层选择面向浏览器插件场景的方案，而不是手工拼装多入口构建。
- **Rationale:** 这是用户明确指定的技术栈。插件友好的构建方案可以降低 manifest、多入口、静态资源与热更新配置复杂度。
- **Alternatives considered:**
  - 手写 Vite 多入口配置：可控，但维护成本高。
  - 普通 SPA 脚手架后期改造成插件：迁移成本高，容易出现构建与运行时偏差。

### 4. Chrome MCP 页面读写能力通过显式服务接口暴露
- **Decision:** 定义如 `readPage()`、`writePage(payload)` 之类的统一接口，并返回标准化结果对象（成功数据 / 错误信息 / 状态）。
- **Rationale:** 对 UI 来说，关心的是“能否读取、读取结果是什么、写入是否成功”，而不是底层调用协议。显式接口能让后续测试、替换实现和补充日志更容易。
- **Alternatives considered:**
  - 让组件直接拼请求参数：实现分散，不利于演进。
  - 用全局事件总线直接传递命令：灵活但不透明，调试成本高。

### 5. 页面读写范围以“最小可验证能力”建模
- **Decision:** 当前仅定义读取当前页面可用信息、向页面提交一次写入请求、展示结果与错误状态的基础能力，不扩展到复杂脚本编排。
- **Rationale:** 本次是架构搭建，不应提前锁定未来业务流程。最小能力足以验证 UI、状态流与服务边界是否成立。
- **Alternatives considered:**
  - 直接支持复杂页面自动化：需求信息不足，风险高。
  - 只搭 UI 不接页面能力：无法验证核心架构是否满足项目目标。

## Risks / Trade-offs

- **[Chrome MCP 服务接口细节尚未完全确定]** → 通过适配层与标准返回模型隔离具体协议，降低后续调整成本。
- **[浏览器插件构建方案选型可能影响后续目录结构]** → 优先使用支持多入口和 manifest 管理的方案，并将业务代码收敛到与构建工具弱耦合的 `src` 结构。
- **[Element Plus 在插件界面中的体积与样式注入成本]** → 初期只使用基础组件，避免过度引入；必要时在后续实现中按需加载或优化样式策略。
- **[不同页面上下文下的读写权限与失败模式复杂]** → 在 UI 和服务层统一设计忙碌、失败、不可用三类状态，避免错误散落在组件中。
- **[当前只做简单入口，后续新增 Side Panel 等时可能出现状态分叉]** → 从一开始就将状态与页面操作逻辑抽离为共享模块，而不是绑定到单个入口组件。

## Migration Plan

- 当前仓库是新项目，无需兼容已有实现。
- 按本设计创建基础工程、UI 入口与 MCP 访问层后，即可基于 capability specs 逐步实现具体功能。
- 如后续发现 Chrome MCP 集成方式需要调整，应优先修改适配层与接口定义，而非让调用方组件直接承担迁移成本。

## Open Questions

- Chrome MCP 服务在实际运行环境中的接入方式、权限要求与返回数据结构是否已有约束文档。
- 初始交互入口最终选择 Popup、独立页还是 Side Panel，是否需要在第一版实现时明确固定。
- 页面写入操作的最小粒度是文本写入、DOM 操作命令，还是更高层的动作封装。
